# 项目方法论（改代码 / 排查 / 验收前先读）

> 目的：把已经踩过的坑和固定流程固定下来，后续会话直接照做，不再靠猜。
> 配套：`tools/precompile_check/README.md`（本地预编译）、`测试.md`（分步验收清单）、
> `计划.md`（步骤状态）、`STEP3_HANDOFF.md`（当前进度与交接）。

## 1. 标准工作循环（每次改代码都走一遍）

1. 阅读顺序：`CLAUDE.md` → 本文件 → `计划.md` → `测试.md` → `STEP3_HANDOFF.md`。
2. **只改本工程** `magic/`、`core/` 下的 `.j`；不直接改
   `KKWE_nncouVer1.5.7.1/jass` 里的副本（那是 WE 实际编译的位置，会被同步脚本覆盖）。
3. 改完立即本地预编译：

   ```bash
   cp /c/Users/admin/Documents/WE/KKWE_nncouVer1.5.7.1/plugin/pjass/pjass-latest.exe \
      /c/Users/admin/Documents/WE/KKWE_nncouVer1.5.7.1/plugin/jasshelper/pjass.exe
   python tools/precompile_check/build_harness.py
   MSYS_NO_PATHCONV=1 cmd.exe /c 'C:\Users\admin\Documents\WE\magic-core\tools\precompile_check\run.bat'
   tail -5 tools/precompile_check/out/compile.log     # 期望 Success! / EXIT=0
   rm -f /c/Users/admin/Documents/WE/KKWE_nncouVer1.5.7.1/plugin/jasshelper/pjass.exe
   ```

4. 同步：`bash tools/sync_to_kkwe.sh`
   （只同步 git 中有变更/未跟踪的文件；`.md` 不同步；输出里应确认目标文件被写入）。
5. 交给作者：YDWE 里 **Ctrl+S** 编译 → 按 `测试.md` 对应步骤在游戏内验收。
6. 作者确认全部通过后再进下一步；同时更新 `测试.md`、`计划.md`、`STEP3_HANDOFF.md`。

**为什么必须按这个顺序**：WE 编译的是 KKWE 目录，不是本工程目录；漏掉同步 = 作者测的是旧代码，
而本地预编译却是新的，极易误判。

## 2. 证据优先：不靠推断下结论

### 2.1 判断地图里有什么（W3X/MPQ）

- 地图头 `HM3W` 占 **512 字节**，MPQ 数据从偏移 512 开始；
  用 Python `mpyq` 打开时需要 `MPQArchive(path, listfile=False)`（listfile 加密不支持）。
- `war3map.j` 是触发器脚本；`war3map.doo` 是**地编摆放的装饰物 + 可破坏物实例**
  （引擎直接加载，**不经过脚本**）；`war3map.w3b` 是可破坏物物体数据，`w3d` 是装饰物，
  `w3u` 单位，`w3t` 物品。
- **`war3map.j` 里 `CreateDestructables` 为空 ≠ 地图里没有可破坏物**。判断方法：
  在 `war3map.doo` 里找实例 ID（4 字符），能在 `w3b` 里找到的是可破坏物，在 `w3d` 里的是装饰物。
- 触发器的 `EnumDestructablesInRect` 能枚举到地编摆放的可破坏物，读不到纯装饰物。

### 2.2 确认代码真的进了地图

- KKWE 的真实编译产物：`KKWE_nncouVer1.5.7.1/logs/inputwar3map.j`（保存地图时生成）。
- 改完代码并同步后，用 `grep` 在 `inputwar3map.j` 里搜新函数名/新日志文本，并看文件时间戳；
  时间戳早于同步时间 = 作者还没重新保存，测了也不算数。

### 2.3 用日志缺行定位线程被中止

JASS 线程中途出错/超限时**只中止当前线程**，后续代码（建触发器、写日志）不会执行。
所以"预期的下一行日志缺失"往往就是线程被中止的信号，而不是功能没触发。

## 3. JASS 运行时限制与预算

### 3.1 单线程字节码上限（约 30 万条）

- 症状：游戏内弹 `JASS ERROR 超过了字节码限制`（不是编译错误），traceback 指向某个函数。
- 后果：该线程**从中途开始全部不执行**。例如 `InitAreaExits` 超限后，
  `[exit] InitAreaExits done` 不会打印，80 个门洞触发器一个都没建。
- 预编译（pjass / clijasshelper）**查不出**这类运行时错误，只能靠游戏内日志和代码预算避免。
- 估算方法：`单次迭代指令数 × 迭代次数`。例如逐点采样 80 个门洞 × 约 270 点 × 10 条指令 ≈ 21 万条，
  再叠加其它初始化就超了。
- 三种解法（按优先级）：
  1. **懒执行**：把一次性大循环推迟到真正需要时，并按项分散（门洞路径快照）；
  2. **定时器分批**：单次回调只做固定小批量，还有剩余就重新武装计时器（刷怪）；
  3. **硬上限**：给扫描/循环加最大次数，超出走兜底并打 WARN。
- 经验目标：单个线程控制在 **3~5 万条**以内，给日志、哈希表、单位创建留余量。

### 3.2 定时器分批模式（刷怪已验证）

- 常量：`ROOM_SPAWN_BATCH = 2`、`ROOM_SPAWN_BATCH_DELAY = 0.03`。
- 状态（`cursor/remain`）持久化在哈希表，跨批次不会重复刷；每批可刷数 = `cap - 场上存活`。
- 续批时新建计时器并把句柄存回 `HT_SPAWN_TIMER`，离场/重置时 `CancelSpawnTimer` 能杀到当前批次。
- 批次开始前先跳过已耗尽的池条目，保证"池里还有怪"判断准确。
- **不要退回"一次刷满 cap"**：单只刷怪最坏要做 24 次随机 + 256 次网格可站立检测。

### 3.3 懒采样模式（门洞原始路径）

- 初始化只做模板捕获，**不**对 20×4 个门洞逐点采样（会超限）。
- 某方向第一次需要封锁时才 `EnsureDoorPathingCaptured`，且必须在生成克隆障碍物**之前**，
  否则会把障碍物自身的阻挡当成"原始状态"。
- 快照在槽位释放/重绑时用于恢复；关卡重置时清空，下一关重新采样。
- 采样点间隔 32（一个寻路格），单次最多 4 个方向。

## 4. 地形 / 可站立判断（极性与覆盖范围）

| API | 语义 | 注意 |
|---|---|---|
| `IsTerrainPathable(x,y,WALKABILITY)` | **true = 路径关闭 = 不可通行**（返回值与名字相反） | 暴雪 GUI 条件原文是 “Terrain pathing … is off” |
| `SetTerrainPathable(x,y,WALKABILITY,flag)` | `flag=true` 恢复通行，`false` 关闭通行 | 与 `IsTerrainPathable` **极性相反** |
| `NNCIsWalkAble(x,y)`（nncou） | 可站立 = 地形可走 **且** 可破坏物不挡 | 内部用隐藏物品试放，能识别树木/岩石 |

- `IsTerrainPathable` **只读地形路径**，看不到树木、岩石、建筑、单位；判断"能不能站"一律用
  `NNCIsWalkAble`（`library ... requires NNCouPoint`）。
- 动态封路仍用 `SetTerrainPathable(..., false)`；恢复时把"是否可通行（1/0）"存下来，
  直接作为 `SetTerrainPathable` 的 `flag` 传回（中间不要再用 `IsTerrainPathable` 的原值）。
- `NNCIsWalkAble` 每次要 `EnumItemsInRect` + 移动隐藏物品，比原生调用贵：
  循环里必须加上限（刷怪扫描 256 次），大批量调用要分批。

## 5. 模板 → 实例模式（门洞障碍物已验证）

固定生命周期，改任何"地编摆放 + 运行时重建"的东西都按这个来：

1. **捕获**（初始化一次）：枚举模板矩形，记录「类型 + 相对矩形中心偏移」，**立即删除原件**。
2. **存内存**：模板表跨关卡保留，后续关卡 `count>0` 就跳过重新读取。
3. **按需重建**：克隆对象只作为实例管理（实例表），清除时逐个 `RemoveDestructable`。
4. **恢复现场**：释放/重绑时先清实例、再恢复路径/状态，然后再按新状态重建。
5. **关卡重置**：清实例表与路径快照，**不清模板表**；下一关继续用内存模板。
6. 重建时 API 读不到的角度/缩放/变体统一默认值；创建失败要重试并打 WARN，不能静默。

## 6. 日志规范

- `TRACE`：高频过程（逐只刷怪、逐单位进出）；默认不可见。
- `INFO`：低频结果（进房调度、清房、传送、模板捕获结果）。
- `WARN`：**不变量被破坏**（找不到刷怪点、创建障碍物失败、池里有怪却刷出 0 只）。
- `ERROR`：无法继续的错误。
- **不要靠调低全局 `debug_level` 排查**；把异常状态提升为 WARN。
- 每条日志尽量带定位信息：`slot=`、`dir=`、`area=`、`terrain=`、数量。
- 验收清单里的预期要写成「日志行 + 行为」两条，缺一不可。

## 8. 坑速查表

| 现象 | 根因 | 处理 |
|---|---|---|
| 初始化后期日志缺失、触发器没建 | 单线程字节码超限，线程被中止 | 懒执行 / 定时器分批 / 加循环上限 |
| 怪物刷在悬崖、树里 | `IsTerrainPathable` 被当成"可走"；且它看不到可破坏物 | 改用 `NNCIsWalkAble` |
| 门洞释放后仍然走不过去 / 原来堵的反而通了 | `IsTerrainPathable` 与 `SetTerrainPathable` 极性相反，快照直接回传导致反转 | 存"是否可通行"，恢复时传 `flag` |
| 关卡 2 之后没有闭门障碍物 | 模板原件在第一关已删除 | 模板表跨关卡保留，`count>0` 跳过重读 |
| 门洞快照把障碍物当成原始地形 | 先建克隆、后采样 | 采样必须在 `CreateSlotDoorDecor` 之前 |
| 地编摆的可破坏物脚本里看不到 | 实例在 `war3map.doo`，引擎直接加载 | 用 MPQ 提取 + `w3b/w3d` 分类判断 |
| 作者测试的是旧代码 | 改完没 `sync_to_kkwe.sh` 或作者没 Ctrl+S | 同步后确认 `inputwar3map.j` 含新代码 |
| `.bat` 在 cmd 里 `cd /d` 失败 | 行尾是 LF | 保持 CRLF |
| JASS 函数/`function X` 句柄未定义 | JASS 没有前向引用 | 被调用者必须先定义（或调整库依赖） |
| 数组/循环越界或房间矩形重叠 | 区域重叠导致进出事件互相干扰 | 物理房间矩形不能重叠；判断无效 ID 用 `< 0` |
| UI 颜色设置后不生效（BACKDROP） | `DzFrameSetVertexColor` 对 BACKDROP 无效（黑图 × 任何色 = 黑） | 颜色只来自贴图本体/帧 alpha/文字色；用预着色 TeamColor/导入贴图 |
| `DzCreateFrame("<模板名>")` 返回 0 / ByTagName 得到空帧绿块 | 模板所在 FDF 没被地图 TOC 加载 | 把模板加进地图导入的 FDF（`ui\MyFrameDef.fdf`）并确保 TOC 加载 |
| TeamColor 颜色与设计值不符（金色变浅蓝/黄色） | MPQ 提取 BLP→PNG 时 **R/B 通道互换**，参考色表整体错位 | 以游戏内运行时颜色为准；真值表见 `UI设计规范.md` §5 |
| 标题/文字 `DzFrameSetTextAlignment` 不居中 | 该 API 在本地图自定义帧上实测未生效 | 用「锚点 + 实测偏移」兜底；不要反复试 align 值 |
| 本地预编译/测试图构建报大量未定义 | `KKWE\logs\inputwar3map.j` 被作者保存别的图覆盖 | 设 `HARNESS_SRC` 指向 `.team/tools/base_inputwar3map_*.j` 历史 base |
| `FlushParentHashtable` 后查询全 false | 清空后该表可能失效（写入计数变但读不到） | 用逐 parent `FlushChildHashtable` |

## 游戏内自动化回归测试方法论（2026-11-10 沉淀）

### 1. 目标与组成
- 目标：改完 JASS 后，不依赖人工进游戏就能判断「行为是否正确、有没有回归」。
- 组成：测试版地图（生产脚本 + 测试库，另存不覆盖源图）+ JASS 断言库 + 报告文件 + 执行器。
- 本轮落地：`test_framework.j`（调度/报告/心跳）+ `test_entry.j`（用例）+ `tools/regression/*`（构建/启动/解析）+ DSH MCP 工具 `mcp__wc3regress__*`（自动拉起，无需授权）。

### 2. 标准流程（一轮约 50~60 秒）
1. `build_test_map`：生产 harness 编译 → 追加测试库 → clijasshelper 全量编译 → 全量复制源图并替换 `war3map.j` → `testmaps/mm-dd_testN.w3x`（源图只读）；
2. `run_regression`：临时把 HKCU 的 Warcraft III InstallPath 指向 H 盘 → YDWE 启动测试图 → 轮询 `Save\war3regression.txt` → 解析 CHECK/SUMMARY → 还原注册表、杀进程；
3. 报告（Preload 文件）即证据：`RUN / LOGS / FORCE / STEP / CHECK / SUMMARY / END`，失败项带现场数据。

### 3. 用例设计三原则
- **先写正确情况**：例如测「未清房封锁」，正确情况是「站进当前区域指定出口 → 使用技能 → 扣血/进冷却/传送到邻居」，先让这条跑绿，再测反例（断边方向不传送、冷却中不传送）。
- **用「设坐标 + 下命令」模拟玩家**：`SetUnitPosition(hero, 门洞中心)` + `IssueImmediateOrder(hero, "neutralspell")`（A07E 基技能 AAns=Neutral Spell 的 order string）；不要直接调用内部函数替代玩家操作。
- **setup / act / check 拆成独立 step**（间隔 0.3s）：区域进出事件、施法事件、槽位回收都是异步结算的，同一 step 里连续做会读到旧状态。

### 4. 状态推进的四个坑
- 跨房间传送前必须 `AllowPlayerLeaveAreaOnce(Player(0))`，否则 areaEnter 守卫会把英雄拉回，造成反复传送甚至卡死；
- 离开一个房间后槽位可能被回收：回来前重新 `Area_EnsureBound(areaId)`，否则 `GetAreaRect` 变 null、坐标变 (0,0)；
- 断言要带证据（坐标/血量/日志计数），失败时不用重新跑就能定位；
- 血量/坐标受自然回复/浮点影响，用容差（`ExpectReal(tol)`），或改成区间断言（如「没有掉 20%」而不是「恰好等于 80%」）。

### 5. JASS 引擎坑（会直接中断测试）
- 单线程约 30 万字节码：日志扫描每个 step 限 2~3 次；一次断言太多会把线程打断、导致报告不落盘；
- `OnTick` 先自增 `stepIndex` 再执行用例：某线程被打断后，下一 tick 仍继续下一个用例；
- `SubString` 的 end 参数是 **exclusive**（用 `probe` 实测确认），子串匹配写法要正确；
- `IssueImmediateOrderById(852600)` 对自定义技能无效，要用基技能 order string。

### 6. 可观测性
- DebugLogger 增加测试 sink：默认收 INFO+，行为用例短窗口 `SetTraceCapture(true)` 收 TRACE；**sink 追加放在级别过滤之后**，否则初始化/选英雄线程会因字符串拼接被推过字节码上限；
- 心跳文件 `war3regression_hb.txt` + bootlog/log 原始文件：卡死时看最后一条心跳即可定位到 step/内部调用；
- 测试就绪后把镜头对准英雄，人工观察不会误判成「英雄还在村庄」。

### 7. 失败判定
- PASS：报告完整（有 `END`）+ checks 全 PASS；`[WARN]` 记录进报告但不阻断；无报告/超时 = FAIL。
- 已知不稳定：偶发游戏卡在加载界面（重跑一次即可）；路径阻断优先用「发移动命令看是否进得了门洞」的行为断言，`IsTerrainPathable` 采样点必须与实现的采样网格（32 步长、min+16 起）对齐。
### 8. 补充坑（2026-11-10，Step 4 实现/回归期间）

- **WAR3 单机暂停**：地图加载完成后，若窗口焦点从 WAR3 转移到其它窗口，游戏会进入暂停（定时器停走、报告不落盘）。
  执行器需在**地图加载期间**把前台让给其它窗口（桌面 / Edge / Explorer 均可），并在等待期间反复保持；
  `run_regression.ps1` 已内置该逻辑（`AppActivate('Program Manager'/'Microsoft Edge'/'File Explorer')`，失败则开一个 Explorer 窗口）。
- **`FlushParentHashtable` 的陷阱**：`call FlushParentHashtable(ht)` 之后该表可能**失效**——
  继续 `SaveInteger` 计数会变，但 `LoadInteger` 恒为 0（表现为「写入成功、查询全 false」）。
  需要清空 hashtable 时用**逐 parent `FlushChildHashtable`**，不要用 `FlushParentHashtable`。
- **揭示/状态类模块的自检**：先做「写入后立刻读回」的自检步骤，能在 1 轮内区分
  「逻辑写错」与「存储层被破坏」，比逐项断言更快定位。
- **聚焦/暂停类问题的心跳特征**：报告文件完全不产生、bootlog/心跳停在某个 step 之前；
  若心跳完全没有更新而游戏进程还在，优先怀疑游戏被暂停（焦点/弹窗），而不是 JASS 线程超限。
