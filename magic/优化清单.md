## 共同前提：现有架构的硬约束

1. **逻辑 ID = 网格坐标**：`RegisterArea` 只接受 `0 .. rows*cols-1`（[data.j:332](map/area/core/data.j#L332)），`Area_EnsureBound`、邻居查询都以 `Grid_IsValidId` 为前提。
2. **邻接 = 网格边**：exit / emergency 直接调用 `Grid_GetNeighbor`（[exit.j:337](map/area/core/exit.j#L337)、[emergency.j:52](map/area/core/emergency.j#L52)）。
3. **物理槽位是临时身份**：同地形房间共享 5 个物理房，空房会被回收并可能被其他逻辑房占用；粘性绑定只是缓存（[slot.j:432](map/area/core/slot.j#L432)）。
4. **全员离场会删怪并回退游标**（[monster_room.j:147](map/area/core/monster_room.j#L147)）。
5. **诅咒按「除 BOSS 外全部可诅咒」计数**（[curse.j:89](map/curse/curse.j#L89)）。

O2/O3 需要先补「矩阵外特殊房」抽象；O5 主要依赖 Step 4 的揭示层。

## O1 固定出生房

**目标**：玩家开局固定出现在矩阵边缘的同一个房间。

**可行性**：低风险。现有 `AreaAddPeripheralEnters()` 注册外围 8 候选，`RollActiveEnter` 随机选 1（[forest.j:345](map/area/config/forest.j#L345)）。改成只注册一个固定坐标，或新增 `AreaSetFixedEnter(chapterId, areaId)` 即可。`InitAreaWithEnter` 会自动把它标成 `ROOM_TYPE_ENTRY`，并把它邻居的 ELITE 降级。

**改动点**：
- `forest.j`：替换起点注册方式。
- `data.j`（可选）：新增固定入口配置接口，保留 `RollActiveEnter` 给其他关卡。

**待定问题**：
- 「固定的几个房间」与「必然在同一个房间」矛盾：固定一个，还是几个候选固定轮换？
- 固定哪个坐标？角落最大度为 2、边中点最大度为 3；随机剪枝后如果只剩 1 条边，开局路线会很窄。

## O2 山洞

**目标**：每局仅一个山洞；有且仅有两个出口，分别链接两个房间（相对坐标任意）；必然有精英怪；地图上标记为紫色；物理房在 20 个普通物理房之外。

**可行性**：中等。本质是一个「矩阵外、度数为 2、邻接显式指定」的特殊逻辑房，直接打破上面的约束 1、2。

**建议方案**：
- **A. 统一方案**：`data.j` 增加显式路线表，exit/emergency 从 `Grid_GetNeighbor` 改为 `Area_GetRoute`；山洞的 2 个方向走显式路线，其余方向封锁。
- **B. 隔离方案**：山洞用专用物理房 + 自定义传送矩形/传送物，完全不进 4 方向门洞模型；只借用 `areaData` 的房间状态与 `areaMonsterRoom` 的刷怪/清房。
- 初步倾向 A（与现有框架一致），B 作为低风险兜底。

**改动点**：
- `data.j`：特殊房注册（绕开 `Grid_IsValidId`）、`Area_EnsureBound` 支持、`InitAreaWithEnter` 跳过特殊房、固定房间类型。
- `slot.j`：支持多个专用/钉住槽位（现有 `terrain < 0` 只支持一个 BOSS 专用槽，[slot.j:483](map/area/core/slot.j#L483)）；专用槽不参与空闲回收/驱逐；重置时清理特殊 ID 的粘性记忆（[slot.j:511](map/area/core/slot.j#L511)）。
- `monster_room.j`：允许预置固定精英组，不要被 `InitMonsterRoom` 的随机绑组覆盖（[monster_room.j:741](map/area/core/monster_room.j#L741)）。
- `curse.j`：特殊房排除诅咒；「全图诅咒」计数改为可诅咒房数量。
- `reveal.j`（Step 4）：紫色图标；非网格边怎么画。

**待定问题**：
- 两个被链接的房间里，洞口怎么呈现？占用某个门洞方向（和原邻居冲突怎么办），还是独立的洞口传送物？
- 山洞是否开局就可见？是否参与诅咒/计时/揭示？
- 未清空时能否用紧急穿越离开？精英状态是否跨进出持久？
- 两个被链接的房间是否允许相同/相邻？

## O3 翡翠梦境

**目标**：每局仅一个翡翠梦境安全房；交互后进入矩阵外的 3 房间一本道关卡；第 3 房必为精英；每名玩家仅一次；梦中死亡直接离开并关闭进入途径；击杀精英给全队永久增益并返回梦境房；逻辑房与物理房完全一致，后进入的玩家看到同一组房间，精英不刷新。

**可行性**：中到大。传送本身不难，难的是「共享且持久的物理房间」和「死亡/退出/增益」的规则闭环。

**关键冲突**：
- 必须使用 3 个专用物理房 + 钉住绑定，不能走共享槽位池；否则槽位回收后另一个逻辑房可能占掉同一物理房。
- `monster_room.j` 在全员离场时删怪并回退游标（[monster_room.j:147](map/area/core/monster_room.j#L147)）。玩家从房 1 走到房 2 就会触发。梦境房必须加「持久」标记跳过。
- `ReleaseAreaIfIdle` 会回收无玩家的 INACTIVE 房间（[enter.j:166](map/area/core/enter.j#L166)）；专用槽 + 钉住可规避。
- `OnRoomCleared` 会加计时、生成祭坛、刷新门洞（[monster_room.j:77](map/area/core/monster_room.j#L77)）；梦境精英清空后要不要这些效果，需要单独钩子/标记。
- `InitAreaWithEnter` / `InitMonsterRoom` 的随机分配要跳过梦境房。

**改动点**：
- 复用 O2 的「特殊房地基」。
- 玩家级状态：hashtable key = playerId（已进入/已死亡/已用）；章节切换时重置。
- 交互物：可复用祭坛的「单位 + 事件 + 每玩家标记」模式；槽位回收时重新生成。
- 精英击杀回调：给 `monster_room.j` 增加公开的「房间清空回调」，或在梦境模块里监听精英死亡。
- 永久 buff：`attr`/`YDHT` 写属性、光环技能或物品；由 GUI/触发器消费。

**待定问题**：
- 翡翠梦境房是矩阵里的随机安全房、固定坐标，还是独立物理房？交互物是什么形态？
- 死亡是立刻传送尸体，还是复活后传送？「关闭进入途径」只关该玩家还是全队？
- 玩家主动离开（非死亡）是否也算用掉一次？
- 精英被击杀后入口是否全员关闭？前两房和精英房的怪物状态是否要求跨玩家、跨进出完全持久？
- 永久 buff 给每个英雄写属性、加光环还是发物品？跨关卡是否保留？
- 梦境中的计时/诅咒/祭坛/奖励规则。

## O4 清房后用技能穿越

**目标**：清空房间后，不再靠「走进门洞自动传送」，而是用与紧急穿越相同的技能进入下一房间；清房状态不消耗生命资源。

**可行性**：低风险。`emergency.j` 已经具备「站在门洞矩形里放技能 → `TryTraverse`」的能力，误触来自 `exit.j` 的门洞进入触发器「走进去就传」。

**改动点**：
1. 去掉 `Trig_DoorEnter` 的自动传送（甚至不注册该触发器），门洞只保留特效。
2. `emergency.j` 的施法处理先判断源房 `IsSourceTraversable`：
   - 可通行（已清空/安全/入口/BOSS）：`TryTraverse(..., false)`，不扣血、不进冷却；
   - 不可通行：`TryTraverse(..., true)`，按现有代价扣血/冷却。
3. 冷却检查挪到「判定为紧急模式之后」，否则免费穿越会被紧急冷却挡住。
4. `IsSourceTraversable` 增加灯塔等新安全房类型（见 O5）。

**待定问题**：
- 技能在 WE 中是否有原生冷却/耗蓝？如果有，免费穿越仍会被卡住；建议原生 0 冷却 0 耗蓝，代价完全由脚本控制。
- 免费穿越是否也要短冷却？
- 门洞判定范围是否要扩大？门洞矩形只有约 160×128（`DOOR_HALF_WIDTH=80`、`DOOR_DEPTH=64`），站偏一点就找不到方向；施法失败要给明确提示。
- 诅咒房封锁退路的 `ShouldBlockEmergencyTraverse` 目前仍返回 false，是否顺手实现？

## O5 灯塔（新增安全房类型）

**目标**：新增安全房类型「灯塔」。支付一定金币后激活，照亮周围 12 格的房间类型，使玩家不需要道路连通即可获知这些房间的类型信息。

**可行性**：合理且可行；主要成本在 Step 4 的揭示层，而不是灯塔本身。房间类型在开局已全量预分配，`GetRoomType(areaId)` 对任意网格房都可用，灯塔只需要触发一次「按距离批量揭示类型」，不依赖 `GetAreaNeighbor`。因此「不需要道路通到这些房间」天然成立。

**已确认：揭开范围**
- 曼哈顿距离 ≤ 2，除中心外正好 12 格（4 个相邻 + 8 个隔一格），与诅咒系统的距离模型一致。
- 靠近地图边缘时实际格数会少于 12，按「半径」处理，不为了凑满 12 格而越界。

**已确认：付费与共享**
- 由发起交互的玩家自行支付金币。
- 揭示结果全队共享，不按玩家分别记录视野。

**改动点**：
- `data.j`：新增 `ROOM_TYPE_LIGHTHOUSE = 6`；建议同时加一个 `Area_IsSafeRoomType(typeId)` 帮助函数，把 SAFE / ENTRY / BOSS / LIGHTHOUSE 统一起来，避免以后每加一种安全房都要改多处判断。
- `exit.j`：`IsSourceTraversable` 纳入灯塔（[exit.j:79](map/area/core/exit.j#L79)），否则激活后玩家无法正常离开。
- `data.j`：`InitAreaWithEnter` 的统计分支补上灯塔（[data.j:705](map/area/core/data.j#L705)）；房间类型注册/权重在关卡配置里加。
- 灯塔模块（建议独立 `lighthouse.j`，类似 `altar.j`）：
  - 每个逻辑房的「已激活」标记（parent key = areaId），跨槽位回收保留；
  - 进入/靠近时的交互物（单位/商店/对话框），支付金币；
  - 激活后调用揭示层接口，批量揭示曼哈顿距离 ≤ 2 的网格房类型；
  - 槽位回收时移除交互物，重新绑定时按激活状态重新生成（复用 `OnSlotAcquire` / `OnSlotRelease` 模式，[forest.j:165](map/area/config/forest.j#L165)）。
- `reveal.j`（Step 4）：提供「揭示某房类型」的公开接口；灯塔只是调用方，不自己维护图标。
- `curse.j`：如果灯塔应保持安全，需要在 `CanCurseArea` 里排除（当前只排除 BOSS）。

**待定问题**：
- 支付方式：复用祭坛的「商店出售激活物品」事件，还是独立的单位交互/对话框？若用商店，需确认金币不足时的交互反馈。
- 激活是一次性永久，还是每局可重复/可刷新？房间被回收再进入时是否保留已激活状态？（建议保留）
- 灯塔是否保证每局至少 1 个？现有 `minCount` 分配是按注册顺序取前面的 UNASSIGNED 房，不是随机；如果要求随机放置，需要额外的放置逻辑。
- 被揭示的是「房间类型」还是也包括精英/BOSS/商店等图标？是否揭示奖励文字？（按目标，只揭示类型）
- 灯塔房间本身是否算安全房（可自由通行、不被诅咒）？
- 是否揭示特殊房（山洞/翡翠梦境）？它们不在网格上，不能用「12 格」表达。

## 实施顺序建议

1. **Step 3 验收后**：O1、O4（小改，互不依赖，能顺便验证门洞/紧急穿越流程）。
2. **Step 4 揭示层落地后**：O5（灯塔），因为它本质是揭示层的一个调用方。
3. **O2/O3 的共同地基**：特殊房注册、专用/钉住槽位、显式路线或自定义传送、（O3）持久房标记 + 清空回调。
4. **O2 山洞** → **O3 翡翠梦境**（O3 规则面最大，先定死亡/复活、入口关闭范围、永久 buff 承载）。
